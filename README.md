# 选图工具 (粗筛合焦照片)

给「拍完一堆 RAW, 想快速过一遍挑出合焦的」用的本地工具。
不做任何修改原文件的动作, 只读 RAW。**图形客户端跑完不写任何文件** —— 报告直接在窗口里看。

## 三种用法

| 方式 | 适合 | 说明 |
|---|---|---|
| **图形客户端** `..\_cull_dist\选图工具\选图工具.exe` | 绝大多数人 | 双击打开, 选文件夹(可多选) → 开始分析 → **结果直接显示在窗口里** → 勾选后点「把勾选的移过去」。**不依赖 Python, 拷到别的电脑也能用** |
| 拖拽窗口 `run.bat` | 习惯命令行的 | 双击后把文件夹拖进窗口回车, 跑完自动打开报告并停留 |
| 命令行 `run.bat "目录" --参数` | 批量/自动化 | 见下面的参数表 |

### 图形客户端怎么用

1. 双击 `选图工具.exe`
2. 「1. 选择照片文件夹(可多选)」→ 可以按住 Ctrl 选多个日期的文件夹
3. 「2. 开始分析」→ 进度条走完, **结果页直接在窗口里出来**
4. 在页面里筛选、点图看大图、勾选满意的
5. 点「选择目标…」→ 勾上「复制(不移动原片)」先试一遍 → 点「把勾选的移过去」→ 确认

> 分析途中想反悔就点 **取消** —— 已经算出来的结果和勾选会一起丢掉,
> 但**文件夹留在列表里**, 直接再点「开始分析」就能重跑, 不用重新选。

> 勾选状态就存在窗口里, **不用再导出中间清单**。移动前一定会弹窗告诉你多少个文件、多大,
> 并且**同名文件只跳过不覆盖**。跨盘移动 (比如 F:\照片 → C:\精选) 也支持。

每张卡片下面有两个按钮: **「打开原图」**用系统看图程序打开, **「在文件夹中显示」**
在资源管理器里定位到那个文件。大图窗口里也有这两个入口。

一张照片里有多张脸时，程序默认取**眼部锐度最高**的那张当主体（不是最大的那张
—— 合影里主角的脸往往不是最大的）。每张多脸照片的卡片上都有一个「主体」下拉，
列出所有检出的脸（`#N 锐度 … 宽 …px`），**你可以手动改**成任意一张 —— 换完
会重算分数和分组，缩略图上亮红粗框也跟着挪。

想**把同组的照片放在一起对比**, 把筛选栏的「排序」从「按锐度」改成
**「按分组, 同组放一起」**: 相似帧组会集中到最上面, 每组前面有一条
「相似帧组 N · X 张」的分隔标题, **点标题可以折叠**; 剩下的单张另起一节。
选「按文件名, 同组放一起」则保持文件名顺序, 但同组的仍挨在一起。

同一批照片第二次点「开始分析」会直接读缓存秒开; 照片有增删改动会自动重扫,
想强制重来就勾上「忽略缓存重扫」。

需要 CSV / 清单存档的话, 页面下方有「导出 CSV…」和「导出勾选清单…」, **点了才会写文件**,
写到哪里你自己选。

### 顺便生成预览 jpg (给 AI 看 / 快速浏览)

操作栏上勾「**生成预览 jpg**」再选一个预览目录, 挑好的照片除了搬过去, 还会**每张额外
生成一张 1600px 的 jpg**, 集中放到那个目录:

```
JC_05478.ARW            ->  精选\JC_05478.ARW
                           预览图\JC_05478.preview.jpg
```

| 项 | 值 |
|---|---|
| 尺寸 | 长边 1600px (A7R III 实际输出 1068x1600) |
| 体积 | 约 180KB/张, 100 张 18MB |
| 速度 | 约 0.3s/张 (重新解码, 不抽内嵌预览图) |
| 白平衡 | 相机自动白平衡, 原样输出 |
| 标记 | **不画**人脸/眼睛检测框 —— 那是给检测结果看的, 会干扰对画面内容的判断 |

> **为什么不能直接抽 RAW 里的内嵌预览图?** 那玩意儿快 300 倍 (0.000s vs 0.30s)、
> 还省一次解码, 但实测 A7R III 的内嵌预览是 **1616x1080 却转了 90 度**,
> 而且**没有 EXIF Orientation 标记**, 任何程序都没法自动转正。
> 拿侧躺的人像给 AI 看, 它给出的修图建议会完全离谱。所以这里老老实实重新解码。

文件名带 `.preview` 后缀是故意的: 既能一眼看出是工具生成的, 也不会跟 Lightroom
导出的同名 `.jpg` 撞名 (那种是修过图调过色的, 含义完全不同)。

### 支持哪些格式

| 类别 | 扩展名 |
|---|---|
| RAW | `.arw .sr2 .sr3 .nef .nrw .cr2 .cr3 .dng .orf .rw2 .raf .pef` |
| 常见图片 | `.jpg .jpeg .png .webp .bmp .tif .tiff` |

同一个文件夹里 RAW 和它的 jpg 导出版都存在时, **只分析 RAW** (jpg 那份是重复的)。
纯 jpg 的文件夹直接丢进去就能分析。

## 命令行参数

```
run.bat "D:\照片\2026-10-01婚礼" --full          # 全分辨率, 更准但慢约 5 倍
run.bat "D:\照片\xxx" --ratio 0.65               # 更严格地判"偏软" (默认 0.55)
run.bat "D:\照片\xxx" --group-ncc 0.8            # 分组更宽松, 会多找一些相似帧 (但可能把换了人的并进一组)
run.bat "D:\照片\xxx" --group-ncc 0.9            # 分组更严格, 宁缺勿滥
run.bat "D:\照片\xxx" --out "D:\输出"             # 指定输出目录
run.bat "D:\照片\xxx" --jobs 8                    # 并行进程数 (默认 4)
run.bat "D:\照片\xxx" --preview-size 0            # 不生成点开放大的大图 (省时间省空间)
run.bat "D:\照片\xxx" --sheet                     # 额外导出检测总览图
run.bat "D:\照片\xxx" --ratio 0.55 --open          # 跑完自动打开报告
```

带了第二个参数就当作命令行调用, 不再停留等按键。
首次运行会自动下载人脸检测模型 (YuNet, 约 230KB) 到 `%TEMP%\cmdc_cull\`。

## 重新打包 exe

改完代码后:

```
venv\Scripts\python.exe build.py
```

产物在 `..\_cull_dist\选图工具\`, 约 180 MB (依赖全在 `_internal`, 不能只拷 exe)。

> **只认 `_cull_dist\选图工具\选图工具.exe` 这一个。**
> 打包的中间目录在 `%TEMP%\cmdc_cull_build\`, 不在 `_cull_tool` 下面 —— 之前放在
> `_cull_tool\_build\` 的时候, PyInstaller 会在那儿留一个"只有 exe、没有 `_internal`"
> 的空壳, 尺寸跟真 exe 几乎一模一样, 很容易误点, 然后报
> **"Failed to load Python DLL ... _internal\python312.dll"**。
> 看到这个报错 = 你双击错文件了, 去 `_cull_dist` 里那份。

## 在客户端里选片, 然后移动文件

**点击缩略图**会打开大图 (1600px), 可以用 `←` `→` 翻页、`Esc` 关闭,
下面有"在资源管理器中显示原文件"。大图是**点开时才解码**的 (约 0.4s),
解码结果存在内存里 (最多 64 张), 所以来回翻已经看过的瞬间打开, **磁盘上不留任何预览文件**。

页面上方有一排筛选: 眼部锐度下限 / 组内占比下限 / 只看组内胜出 / 只看有可比对对象的组 /
对焦依据 / AF区域, 以及"显示 N / 54 张"的实时计数。

勾完之后直接点 **把勾选的移过去** 就行, 不用导任何中间文件。

> **为什么以前要"导出清单"再搬?** 那时报告是用外部浏览器打开的, 浏览器出于安全沙箱,
> 网页里的 JS 读写不了你硬盘上的文件, 只能导一个 txt 出来再让 Python 搬。
> 现在报告和 Python 在同一个 WebView2 窗口里 (走 `chrome.webview.postMessage` 桥, 不开端口、
> 不弹防火墙), 网页可以直接喊 Python 搬文件, 这道坎没有了。

### 也可以完全不碰网页, 直接用阈值挑

```
run.bat "D:\照片\xxx" --keep-to "D:\照片\精选" --best-per-group --dry-run   # 先看会动哪些
run.bat "D:\照片\xxx" --keep-to "D:\照片\精选" --best-per-group             # 真动
run.bat "D:\照片\xxx" --keep-to "D:\照片\精选" --min-ratio 0.9              # 只留组内占比>=90%
run.bat "D:\照片\xxx" --keep-to "D:\照片\精选" --min-sharp 1500             # 只留锐度>=1500
```

| 参数 | 含义 |
|---|---|
| `--keep-to DIR` | 把挑中的文件移动到这个目录 (不存在会自动创建) |
| `--keep-from FILE` | 读清单文件移动; 给了这个就**不再重新分析**, 直接搬 |
| `--best-per-group` | 每组只留最锐的那张。**单张照片照原样保留** |
| `--min-ratio R` | 组内占比 ≥ R (0~1)。只对多帧组有效, **单张视为通过** |
| `--min-sharp X` | 眼部锐度 ≥ X (绝对值, 跨照片不可比, 慎用) |
| `--copy` | 复制而不是移动 (更安全) |
| `--with-jpg` | 连同名 `.jpg` 一起搬 |
| `--dry-run` | 只列出会动哪些文件, 不动真格 |

**安全设计** (都是实测过的行为):

- `--with-jpg` 不带就**只搬 RAW**; 同名 `.xmp` / `.acr` 编辑记录**一定会跟随**,
  不然你的 Lightroom 修改会和照片分家。
- 目标位置已有同名文件时**跳过, 绝不覆盖**。
- 目标 == 源目录时直接拒绝。
- 清单里不存在的文件名会被列出来而不是静默忽略。
- `--dry-run` 保证一个文件都不动。
- 每次移动都追加写 `_cull_out\移动日志.txt`。

### 速度

54 张 42MP 的 ARW 实测 (本机 20 核):

| 配置 | 总耗时 |
|---|---|
| 1 进程 (串行) | 26.0 s |
| 2 进程 | 19.2 s |
| **4 进程 (默认)** | **12.7 s** |
| 8 进程 | 13.3 s |
| 4 进程 + 2048px 大图 | 13.0 s |

只跑到 2 倍而不是 8 倍, 是因为瓶颈在 RAW 解码: 磁盘不是问题 (F: 实测 2560 MB/s,
86MB 一张只要 34ms), 限制来自解码本身的内存带宽。加更多进程收益就没了。
单张的时间构成: 解码 317ms / 缩略图 / 人脸检测 80ms / 读文件 32ms /
**眼睛锐度计算只有 1ms**。

> 踩过的坑: OpenCV 默认会开满所有核 (本机 20 线程), 4 个进程就是 80 线程抢 20 个核,
> 实测把总耗时从 13 秒拖到 **44 秒**。所以多进程时脚本会把每个进程的 OpenCV 线程数压到 1。

## 输出

**图形客户端 (`选图工具.exe`): 默认什么都不写。** 结果在窗口里看, 大图在内存里,
想存档点「导出 CSV…」自己选位置。只有你真的点了导出, 或者真的移动了文件, 才会落盘。

**命令行 (`run.bat` / `cull.py`): 写到 `<照片目录>\_cull_out\`**

| 文件 | 内容 |
|---|---|
| `选图报告.html` | 缩略图对比页: 点图放大、可筛选、可勾选、可导出清单 |
| `选图报告.csv` | 每张的分数 + EXIF + AF 设置, Excel 里可自行排序筛选 |
| `各组最佳.txt` | 相似帧分组明细, 组内标出建议保留的那张 |
| `疑似模糊.txt` | 组内被判定偏软的那几张 |
| `preview/` | 点开放大用的 2048px JPEG (平均 235KB/张, `--preview-size 0` 可关) |
| `移动日志.txt` | 每次移动/复制都追加记录 (用 `--keep-to` 后才有) |
| `检测总览.jpg` | 加 `--sheet` 才有, 用来核对人脸/眼睛检测是否准确 |

## 它怎么算的

1. `rawpy`(libraw) 真正解码 RAW, 拿原始像素 (默认半分辨率, 约 0.3 秒/张), **多进程并行**
2. OpenCV **YuNet** 轻量 CNN 做人脸检测, 同时给出双眼等 5 个关键点
3. 在眼睛位置的原始像素上算 **Tenengrad 梯度能量** —— 合焦的眼睛边缘锐利,
   跑焦的边缘被抹平, 这个值会掉下来
4. 把「脸的位置 + 脸的大小 + 焦距」都几乎一样的帧聚成一组 (同一姿势的复拍/连拍),
   组内挑出最锐的那张, 组内偏软超过阈值的标为"疑似模糊"
5. 另外读 Sony maker note 的 AF 设置 (对焦模式/区域/对焦点坐标)

## 关于 Sony AF 元数据 (实测结论: 大部分情况拿不到)

脚本会读 Sony maker note 里三个**未加密**、可直接解析的标签:

| 标签 | 含义 |
|---|---|
| 0x201b | FocusMode (AF-S / AF-C / AF-A / DMF / Manual) |
| 0x201c | AFAreaModeSetting (Wide / Zone / Center / FlexibleSpot) |
| 0x201d | FlexibleSpotPosition — **对焦点坐标**, 仅 Flexible Spot 模式有效 |

拿到坐标时会在缩略图上画一个**绿色十字**, 一眼看出相机对在哪 (红框=人脸, 青框=眼睛)。

**但有个硬限制**, 实测这批 54 张 (A7R III + 原厂 FE 镜头):

- 51 张是 `AF-A + Wide`(广域), 坐标全是 (0,0)。广域模式下相机自己选点,
  而 **ILCE 机型不记录它实际选了哪个点** —— 那段数据在加密的 0x94xx 块里,
  连 ExifTool 都没解开 (源码里直接标注为 `Sony_0x9402` / `unknownCipherData`)。
- 只有 3 张用了 FlexibleSpot, 拿到了真实坐标。
- 更关键的是: A7R III 解密后能读出的对焦相关标签**一个都没有**。
  `0x940e`(AFInfo, 含 AFPointAtShutterRelease)只有 SLT/ILCA 机型或转接
  LA-EA2/EA4 相位对焦环时才有数据; `0x2020`(AFPointsUsed)只对 A 卡口有意义;
  老款 DSLR 的 `FocusInfo`(FocusPosition/FocusDistance)对 ILCE 不适用。

**所以: 如果你想要"相机到底对在脸上还是背景上"这个判断, 得改用 Center 或
Flexible Spot 拍摄才能拿到数据。** 用 Wide 拍的话, 这条路是堵死的, 不是脚本的问题。

> 顺带一个有用的例子: JC_05546 用了单点对焦, 绿十字正好压在眼睛上 —— 说明这张
> 眼睛大概率是合焦的; 但它的眼部锐度只有 294(偏低)。这正好印证下面的说明:
> 低分是指标的缺陷, 不一定是照片糊了。

## 关于准确度 (重要)

这个脚本能可靠做到的是: **找出人脸位置** 和 **把一批照片按"眼睛区域锐度"排个序**,
让你从上往下扫一遍就能快速过掉明显跑焦的。

但要说清楚它的边界:

- 眼睛区域的梯度能量会**同时受框景大小和光线影响**。近景特写脸上大片平滑皮肤,
  裁切区里高频细节本来就少, 分数天然偏低; 中远景画面里塞满头发、睫毛、草叶边缘,
  分数天然偏高。所以 **跨照片的绝对值不能直接比清晰度**。
- 只有 **同一组 (几乎同一姿势)** 的帧之间比较才是可靠的 —— 这也是脚本把
  "疑似模糊"限制在组内判断的原因, 组的门槛卡得比较严 (`--group-ncc`, 默认 0.85)。
- 一张图里有多张脸时, 脚本取**眼部最清楚的那张**当主体 (不是最大的那张 ——
  合影里主角的脸往往不是最大的)。但这也意味着主体可能在人之间跳, 这种组
  会在卡片上标 ⚠, 提醒你组内锐度不可比。
- 自动判定会有误报和漏报, **最终请以 `选图报告.html` 里肉眼复核为准**。
- 眨眼、表情、姿态这类判断脚本不负责, 那些需要专门的模型 (Aftershoot / Imagen /
  Narrative Select 这类商业工具就是靠这些吃饭的)。

一句话: 它是个"帮你把候选排好、把明显废片挑出来"的辅助, 不是替你按下最终决定的工具。

## 已知环境问题

- **客户端的界面是 WebView2 (Edge 内核)**, 靠 `pywebview` + `pythonnet` 驱动。
  页面和 Python 之间走 `chrome.webview.postMessage`, **不开本地端口, 不弹防火墙**。
  没装 WebView2 运行时的话, `app.py` 启动时会弹窗提示并退出 (不会默默退回已废弃的 IE 内核)。
- **打包后白屏 = `webview/js/` 没进包。** pywebview 用 `os.path.realpath(__file__)` 去读
  它的 js 目录, 而 PyInstaller 默认把纯 Python 塞进 `base_library.zip`, `open()` 读不到。
  所以 `app.spec` 里必须 `collect_all('webview')` (pythonnet 同理)。
  排查顺序: 先看 `_cull_dist\选图工具\_internal\webview\js\api.js` 在不在。

- **轮询必须用递归 setTimeout, 不能用 setInterval**: `setInterval(async ...)` 会重入 ——
  上一次 `await api.poll()` 还没回来, 下一次已经发出去了。pywebview 的 JS 侧用
  `valueId` 存回调, 两个 poll() 撞在一起会互相覆盖, **消息进了错的任务**。
  症状是界面永远停在"正在分析…"、进度不动、取消也没反应, 但 Python 那边其实跑得好好的。
  `ui.html` 里是 `pollOnce()` 递归排下一次, 并且 `handleMsgs` 外面包了 try/finally ——
  单条消息处理出错也不能让轮询停摆。
- **跨盘移动**: `os.path.commonpath` 在 F:\ 和 C:\ 之间会抛 `ValueError`, 所以
  `do_move` 先比盘符再算公共路径。搬到别的盘是支持的。
- **`IMG_EXTS` 和 `decode()` 必须同步**: 加了新后缀但 `decode()` 没认, 它就会掉进
  rawpy 分支, 然后报"找不到内嵌预览图" (那是给 RAW 用的兜底, 对普通图片没意义)。
  `decode()` 现在按 `IMG_EXTS` 判断, 所以两个地方是一起改的。
- **内嵌预览图不能用**: 抽 RAW 里的内嵌 JPEG 看着很诱人 (0.000s vs 0.30s, 快 300 倍),
  但实测 A7R III 的内嵌预览**转了 90 度**且**没有 EXIF Orientation 标记**,
  程序无法自动转正。预览 jpg 必须重新解码 (0.3s/张)。
- **预览要在搬文件之前生成**: 勾了"移动"的话, 搬完源文件就没了, 再生成就找不到源了。
  `Api.move()` 里预览先做, `do_move` 后做。
- **取消用标志位而不是 `run_id`**: `cancel()` 只置 `_cancel` 事件。如果它也递增
  `_run_id`, 后台线程会以为任务已过期直接退出, 于是**不发 `idle`**, 界面会永远卡在
  "正在分析…"。`_run_id` 只在 `analyze()` 开始新一轮时递增。
- **队列按钮要同步改 Python 状态**: 界面上的 × 如果只删 UI 列表, Python 那边还留着路径,
  再加回来会被 `add_folders` 当成"已存在"跳过 —— 那个文件夹再也分析不了。
  所以 × 调的是 `api.remove_folder()`。
- **多进程 + 打包**: Windows 用 spawn 启动子进程, 打包成 exe 后必须调
  `multiprocessing.freeze_support()`, 否则子进程会重新执行整个模块并无限递归。
  `app.py` 和 `cull.py` 的 `__main__` 里都有。
- **OpenCV 线程超订**: OpenCV 默认开满所有核, 4 个进程就是 80 线程抢 20 核,
  实测把 54 张的处理从 13 秒拖到 **44 秒**。所以多进程时每个进程的 OpenCV
  线程数被压到 1。
- `run.bat` **故意只用 ASCII 字符**。cmd.exe 读取 .bat 时按控制台代码页解析,
  里面写中文会被拆成乱命令 (实测过), 所以中文提示全部放在 `cull.py` 里,
  由 `chcp 65001` 保证正常显示。改动这个 bat 时请保持纯英文。
- **OpenCV 在中文路径下打不开文件**, 所以模型会被复制到纯英文临时目录。
  照片目录本身含中文没问题 (走的是 Python 文件 API 和 rawpy)。
- `opencv-python` 5.x 移除了 Haar 级联检测器, 且 headless 包不带级联 xml,
  所以这里用 YuNet 而不是 Haar。需要用 4.x。
